# Project Log

## 2026-09-16 — Plano concluído: run-half (estimate → emit → report + exemplo moonlighter)

O MVP fechou: `suite.yaml` lido pela primeira vez, `estimate` (chars÷4, juiz só em caso com rubrica, tabela `prices.yaml` datada), `emit` (config promptfoo com assert JS por caso, parser tolerante dentro do assert, shim Python escrito uma vez, `--format jsonl`) e `report` (flaky por repetição, discordância entre juízes, custo real contra estimado, `--baseline`), mais o exemplo real contra o `classify_response` do moonlighter commitado em `examples/`, o CI validando o config com o promptfoo de verdade e o gate de cobertura em 1.0. Antes do plano, três dúvidas do handoff foram medidas rodando o promptfoo 0.123.0: `cost` é só do alvo, o provider Python chama a função real, o MCP valida o config gerado. A execução expôs dois defeitos do plano 1 que nenhum teste via: `forge cases` devolvia `input: {}` contra qualquer modelo real (schema `z.record` sem `properties`; corrigido na Task 4b, teste live agora cobre `cases`) e o shim do exemplo, escrito no próprio plano, apagava o corpo dos e-mails — o primeiro eval "48/48" era artefato; com corpo de verdade a suíte deu 45/48 com um caso flaky, que é o relatório fazendo o que existe pra fazer. A revisão whole-branch achou o que as revisões por task não podiam: `emit` gerava assert vazio (passa com qualquer JSON) quando o `expected` deixava de bater com o oráculo do cenário, alcançável pelo fluxo documentado de editar o oráculo no `review`; e `report.md` nunca nomeava um caso que falha em todas as repetições, porque a lista de bullets da spec não pedia — ambos corrigidos na onda final, com mais oito Important (cenário pendente sumindo em silêncio com `include` vazio, "pendente" dito de item rejeitado, pipe quebrando tabela, custo não medido impresso como $0 e -100%, pass rate contando erro de provider como reprovação). Ficaram de fora, por decisão: tokenizer real, `forge run`, MCP, histórico multi-run, e 20 pendências pequenas triadas no BACKLOG.
→ plan: `docs/superpowers/plans/2026-09-15-run-half.md`

## 2026-09-15 — Plano concluído: core-pipeline (describe → scenarios → cases → dedupe → import → review)

O MVP da forja está de pé: biblioteca + CLI em TypeScript/bun, provider via Vercel AI SDK (anthropic, google, openai, ollama e um `fake/` para teste), tudo em arquivos YAML dentro de `.forge/`. Onze tasks executadas por subagente, cada uma revisada contra o próprio brief — e a revisão whole-branch no fim achou seis defeitos que nenhuma revisão por-task podia ver, todos da mesma família: o verbo relatava sucesso sem ter feito o trabalho. Corrigidos nesta mesma branch: o gate de feature pendente valia em um verbo de três; `describe` destruía uma feature já revisada em silêncio; uma edição que mudava o id era descartada e contada como "1 edited"; `review --scenario` desconhecido respondia "nothing pending" e saía 0; `dedupe` escrevia um arquivo de casos vazio; e o contrato de oráculo valia para o modelo mas não para a pessoa (Enter no prompt gravava `expected: {label: ""}` como aprovado). Ficou de fora, por decisão: `emit` para promptfoo, execução da suíte e estimativa de custo — são o plano 2.
→ plan: `docs/superpowers/plans/2026-09-14-core-pipeline.md`

## 2026-09-14 — Spec novo: llm-test-forge (design do MVP)

Nasce do veredito viável da bancada (investigação de 13/09/2026): o mercado cobre executor e avaliador (promptfoo), e ninguém cobre a forja — descrição → cenários de tipos mistos → casos com saída esperada → revisão humana em arquivo → estimativa de custo antes → discordância entre juízes e instabilidade depois. Decidido em brainstorming: formato em camadas (casos + suíte, promptfoo gerado dos dois), TypeScript com bun, lib + CLI primeiro e MCP depois, Vercel AI SDK, entrada em texto livre com prompt opcional, revisão em arquivo com CLI interativa, pipeline inteiro fino com dedupe semântico e `import` de logs por contrato JSONL.
→ spec: `docs/superpowers/specs/2026-09-14-llm-test-forge-design.md`
